# План реализации блока 1

Дата: 2026-09-13. Цель: локально запускаемый кабинет, в котором владелец загружает материалы BASIS и проверяет автоматически опубликованные продуктовые знания. Разработка с нуля. Старый Otdel служит источником дизайна и Отто, не серверного кода.

## Результат, который можно принять

Добавить партнёра → загрузить два настоящих PDF → увидеть состояние каждой страницы → получить направления и факты → открыть страницу-доказательство → задать вопрос → увидеть ответ с условиями либо честный пробел → добавить новый материал → увидеть новую версию без потери предыдущей.

Автопубликация действует по правилам. Кнопка ручного одобрения каждого паспорта не требуется. Публикация знаний не означает разрешение на рассылку, сделку или обещание технической совместимости.

Текущая задача готовит план, дизайн-прототип и процесс разработки. Функции 1A–1F ещё предстоит реализовать. Наличие макета и зелёной проверки репозитория не означает работоспособность продуктового блока.

## Решения по устройству

- Rust: HTTP API и worker, модульный проект. Общие domain/application слои; Axum/Tokio/SQLx — выбранное направление библиотек, версии фиксируются при 1A.
- PostgreSQL: рабочие данные, очередь, транзакции, RLS и поиск; pgvector для embeddings. Сначала точный поиск на небольшом корпусе, ANN только после проверки полноты с фильтрами.
- React + TypeScript + Vite: кабинет. Серверная бизнес-логика остаётся на Rust. TypeScript нужен браузерному интерфейсу, не заменяет выбранный backend.
- S3-совместимый адаптер оригиналов; конкретная реализация локального/серверного хранилища определяется в 1A. Изолированные адаптеры PDF/OCR, поиска и моделей.
- Публичный GitHub содержит код, план, дизайн и синтетические тесты. Реальные PDF, реестры, письма, ключи и результаты платных запусков — вне Git.
- Папки будущего приложения: `crates/domain`, `crates/application`, `crates/infrastructure`, `apps/api`, `apps/worker`, `apps/web`, `migrations`, `tests/fixtures`, `tests/e2e`. Это план, а не уже существующие каталоги.
- Отдельные модули: partners, materials, extraction, knowledge, research, retrieval, publication, jobs, access. Между слоями типизированные контракты. UI не получает прямой доступ к SQL или файловому хранилищу.

## Подготовка P0 — текущая задача

- Сохранить визуальную систему правильного Otdel: графит, тёплое золото, Manrope, красный Отто.
- Выпустить дизайн-контракт и кликабельный прототип с ясной маркировкой демонстрации.
- Создать репозиторий, рабочие ветки, отдельные worktree, CI, правила PR, issue-шаблоны и список задач.
- Проверить макет на 360/768/1440 px, клавиатуру и отсутствие выдачи демонстрации за реальную обработку.
- Защитить main обязательной проверкой; интегрировать изменения после ревью и успешного CI.

Выход P0: можно открыть макет, прочитать план и запускать исполнителей по конкретным заданиям.

## 1A — рабочая оболочка, партнёр и приём материалов

Зависимость: P0. Владелец результата: Claude backend; UI-задача после фиксации контракта API; QA после объединения.

Задачи:

1. Зафиксировать toolchain/dependencies, Cargo workspace, web workspace, контейнеры PostgreSQL и хранилища, воспроизводимые команды запуска. Проверить локальное наличие Rust или документировать контейнерный запуск.
2. API, health/readiness, конфигурация без секретов в логах, миграции, доступ к бюро и партнёру. Вход владельца и явное разделение локального dev-режима и рабочего режима.
3. Карточка партнёра с минимальным вводом; кандидаты реквизитов не становятся подтверждёнными автоматически.
4. Приём PDF/изображений потоково, лимиты, hash, проверка типа и карантин. Согласованное поведение при сбое между записью файла и БД, сверка сиротских объектов.
5. Задания/попытки/lease, дедупликация, остановка и повтор, базовый журнал. Никаких внешних API внутри длинной транзакции БД.
6. Подключить настоящий UI материалов к API, включая сохранённое состояние после перезагрузки. PDF ещё не объявлять прочитанным.

Контракт: partner_id, material_id, source_revision, job_id; структурированная ошибка с кодом, причиной и допустимым повтором. OpenAPI и клиентские типы создаются здесь; изменение контрактов — зона Codex.

Приёмка: оба BASIS PDF сохранены и доступны только нужному владельцу; повтор не создаёт дубль; файл с неверным типом отклоняется; сбой записи виден; после перезапуска карточка сохраняется; запрос партнёра A не читает файл B. Миграции, Rust unit/integration и browser journey проходят.

## 1B — чтение документов, OCR и таблицы

Зависимость: 1A.

1. Выделить pipeline по страницам: текстовый слой → оценка пригодности → OCR для изображений → структурные элементы.
2. Фиксировать parser/OCR версии, время и исход каждого этапа; повторить только проблемную страницу.
3. Хранить текстовые области, таблицы, заголовки, сноски и координаты. Изображения схем опирания сохранять как часть доказательства таблицы.
4. UI исходника с номером страницы и подсветкой области; честный статус частичного чтения.
5. Выбрать OCR/vision на небольшом контрольном наборе BASIS до массового запуска, с учётом языка, таблиц, задержки, стоимости и правил передачи.

Приёмка: учтены все 32 + 12 страниц. Презентация не считается пустой. Контрольная таблица BP 21/21D сохраняет длину, толщину, единицы и схему нагрузки. Неясная ячейка остаётся неизвестной. Ошибка страницы не даёт статус полного извлечения. Источник открывается точно.

## 1C — продуктолог и структура знаний

Зависимость: 1B.

1. Определить JSON-схемы результатов ролей, ограничения размера и валидатор Rust. Отказ и некорректный ответ модели — явные исходы.
2. Выделить направления, семейства, изделия и услуги; связать каждый вывод с источником.
3. Извлечь значения с единицами, условиями применимости и статусом; создать глоссарий, применения, Q&A и пробелы.
4. Смысловые чанки с отделённым производным контекстом; версия embedding-профиля.
5. Подключить UI знаний и пробелов. «Подтверждено источником» не называть независимой проверкой производителя.

Приёмка: контрольные поля сверены с оригиналом; не смешиваются продукты и свойства; цена/срок не выдумываются; глоссарий различает неоднозначные термины; значения без доказательства не используются как факты.

## 1D — исследователь и закрытие отраслевых пробелов

Зависимость: 1C.

1. Продуктолог формирует конечный список вопросов, а не запрос «исследуй всё».
2. Ввести search/fetch adapters, паспорт провайдера, ограниченный доступ сети, лимиты и источник факта.
3. Транзакционный резерв бюджета, учёт факта/неопределённого расхода, конкуренция заданий и предел проходов.
4. Разделить отраслевое знание и утверждение о конкретном партнёре. Не копировать характеристику конкурента в паспорт BASIS.
5. Сформировать вопросы производителю. До подключения коммуникаций статус — «подготовлен, канал не подключён», а не «отправлен».

Приёмка: существенные выводы подтверждаются открытым источником; исчерпание бюджета останавливает исследование; временный сбой не превращается в факт; повтор запроса не даёт бесконечных расходов; ограниченная проверка выполняется с настоящим провайдером после настройки.

## 1E — проверяющий, публикация и поиск

Зависимость: 1D.

1. Отдельный контекст проверяющего: утверждения + оригинальные доказательства, без доверия к объяснениям продуктолога.
2. Правила статусов и готовности по задачам; разрешённые факты не включают неизвестные/спорные условия.
3. Неизменяемая версия знаний, атомарный указатель published, защита от позднего результата старого запуска.
4. Гибридный поиск: точные значения, текст, векторы; обязательный scope и закреплённая версия. Отдельные ответы «недостаточно данных».
5. UI Q&A с доказательствами, ограничениями и ссылкой на пробел; автопубликация без обязательного ручного согласования.

Приёмка: запросы об артикуле, перефразировании, неизвестном, противоречии и чужом партнёре; нет смешения версий; опубликованная ограниченная готовность видна; обещание применимости не выводится только из похожего текста.

## 1F — обновления, расширение входов и полная приёмка

Зависимость: 1E.

1. Инкрементальное обновление по новому документу/вопросу, зависимости фактов/Q&A, отзыв ошибочного факта, сравнение версий и безопасный откат.
2. DOCX/XLSX/PPTX и веб-ссылки; отдельные тесты таблиц/страниц. Если формат не реализован, он не проходит приёмку как поддерживаемый.
3. Ссылка загрузки партнёру и API материалов: квоты, срок действия, scope, отзыв ссылки. Почта/мессенджеры/Drive/видео — отдельные подключаемые задачи после выбора конкретного сервиса; они не притворяются подключёнными.
4. Экспорт паспорта из опубликованных данных с источниками. Презентационные экспорты — отдельное улучшение после базового документа.
5. Настраиваемая перепроверка источников; версии инструкций и набор регрессий, без бесконтрольного самоизменения агента.
6. Восстановление БД/файлов, повтор запуска worker, негативные сценарии, доступность, нагрузка и пользовательский прогон.

Приёмка: реальный сценарий ниже пройден и воспроизводим. Ограничения перечислены; неподключённые внешние каналы не объявляются готовыми. Владелец пробует приложение и даёт замечания; устраняем их до блока 2.

## Финальная демонстрация владельцу

1. Открыть чистый рабочий кабинет, создать BASIS.
2. Загрузить два настоящих каталога и уйти с экрана. Вернуться и перезагрузить страницу: прогресс и данные сохранены.
3. Открыть обработанные страницы и контрольную таблицу. Показать, как система объясняет проблемную ячейку.
4. Открыть продукт, термин и применение. По факту перейти к источнику.
5. Задать вопрос с известным ответом, затем запросить отсутствующую цену/срок. Увидеть разные, правильные исходы.
6. Добавить контрольный изменённый документ. Показать новую версию, изменения и сохранённый оригинал.
7. Повторить загрузку и воспроизвести сбой обработки. Продолжить без дублей и утраты прогресса.
8. Проверить второй тестовый контур партнёра; закрытые данные первого недоступны.
9. Открыть ограничения готовности и расходы; сопоставить с выполненными заданиями.
10. Повторить основной путь на узком экране и с клавиатуры.

Необходимый пакет: инструкция запуска, заполненные результаты UAT, короткое видео/скриншоты, версии кода/моделей/провайдеров, перечень известных ограничений. Реальные документы и скриншоты с закрытыми данными не публикуются автоматически.

## Исполнители, ветки и зависимости

| Исполнитель | Рабочая ветка сейчас | Зона ответственности |
|---|---|---|
| ASTRA | astra/block-01-plan | Архитектура, спецификация, задачи и приёмка |
| Claude Design | claude/design-system | Дизайн-контракт, токены и прототип |
| Claude Platform | claude/dev-platform | CI, инструкции, команды и шаблоны |
| Claude QA | claude/qa-review | Независимый обзор, тестовые сценарии, отчёт |

Для реализации создаются ветки задач `claude/backend-1a`, `claude/frontend-1a` и следующие. Не создавать одного вечного параллельного редактирования: каждый task имеет владение файлами, базовый SHA и собственный worktree. Backend-контракт предшествует frontend-интеграции. QA получает уже объединённый кандидат.

Все межэтапные зависимости обязательны. Параллельность допустима только внутри текущего этапа при непересекающихся файлах и готовых контрактах. Миграции и API-контракты имеют одного владельца на этап.

## Что фиксируется в каждой задаче Claude

Цель, исходная версия, owned files, сценарий пользователя, ограничения, команды проверки и формат отчёта. Сессия/курсор/текущее состояние хранятся локально в игнорируемом `docs/worker-runs/`; публичные issue содержат только очищенные требования.

Claude не пушит и не мержит сам. ASTRA проверяет diff, запускает соответствующие проверки, возвращает ошибки в ту же сессию, затем создаёт PR. Зелёный CI дополняет, но не заменяет содержательное ревью. После интеграции проверяется общий результат. Удаление worktree — только после сохранения всей работы.

## Ресурсы и внешние зависимости

Перед 1A: выбрать серверный путь запуска и хранилище; локально сейчас найден Docker, отдельный Rust toolchain не найден. Перед 1B/1C: определить OCR, модели, допустимую передачу документов и лимиты. Перед 1D: поиск и бюджет. Эти решения не заменять случайным платным провайдером.

Пока нет измерений, календарные сроки и скорость обработки не обещаются. Прогресс измеряется принятым работающим этапом, а не числом созданных файлов. Численные цели p95/памяти/стоимости фиксируются перед нагрузочной приёмкой на согласованном оборудовании.
