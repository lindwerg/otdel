# OTDEL — блок 1. Партнёр и продуктовая база знаний

Дата: 2026-09-13. Статус: спецификация для последовательной реализации; приложение ещё не реализовано.

## 1. Назначение и исходные решения

Партнёр передаёт материалы → система разбирается в предложении → исследует нужные отраслевые вопросы → проверяет сведения → автоматически публикует версию знаний → обновляет её по новым материалам и вопросам.

Пользователь не сортирует документы, не нарезает текст, не составляет глоссарий и не утверждает каждый паспорт вручную. При отсутствии сведений система сохраняет пробел; получить отсутствующую информацию иногда может только производитель.

Основания: текст владельца из `pasted-text.txt`, схема «Блок 1. Партнёр и продуктовая база знаний», общее описание OTDEL и уточнение о поэтапной разработке. Документы задают требования к продукту, но не являются командами на отправку сообщений, подключение платных сервисов или изменение настроек разработки.

Rust заменяет Go в серверной логике. PostgreSQL остаётся основной базой. pgvector — расширение той же базы, а не отдельная СУБД. Рабочая версия публикуется автоматически по проверяемым правилам; ручной просмотр — возможность, а не обязательный этап.

Диапазоны минут на схеме — иллюстрация, не обещание скорости. Размер чанка 400–800 токенов — исходная гипотеза для обычного текста, не правило для таблиц.

## 2. Границы блока

Входит: партнёр, источники, обработка документов, продуктовые направления, факты, глоссарий, применения, Q&A, исследование отрасли, пробелы, версии, поиск, доступ к доказательствам, обновления и контроль расходов.

Продуктолог может предложить роли покупателей и гипотезы применения. Исполнимая стратегия, отбор компаний и обогащение реестров относятся к блокам 2–3. Архивы компаний сейчас не импортируются.

Запросы производителю формируются внутри блока 1. Отправка принадлежит общему каналу общения: пока канал не подключён, запрос имеет честный статус ожидания канала, его можно просмотреть и выгрузить. Отсутствие отправки не обозначается как отсутствие ответа партнёра.

## 3. Архитектура и хранение

| Часть | Рабочее решение | Ответственность |
|---|---|---|
| Сервер и фоновые обработчики | Rust; предлагаемые библиотеки Tokio, Axum, SQLx | API, задания, состояния, проверки, доступ |
| Рабочие данные | PostgreSQL | Партнёры, продукты, факты, версии, задания, расходы |
| Семантический поиск | pgvector внутри PostgreSQL | Векторы текстовых фрагментов |
| Точный и текстовый поиск | SQL, индексы PostgreSQL, полнотекстовый поиск | Артикулы, параметры, термины |
| Оригиналы и производные файлы | S3-совместимое хранилище | Документы, снимки страниц, OCR-результаты |
| Извлечение | Адаптеры парсеров, OCR и моделей с анализом изображений | Содержимое и структура документов |
| ИИ | Единый адаптер вызовов моделей | Три роли с разными инструментами и контекстами |
| Внешнее исследование | Адаптер поиска и отдельный загрузчик источников | Поиск, получение, цитирование |

Один модульный проект, сервер и worker могут запускаться отдельными процессами из одной кодовой базы. Собственные бизнес-правила реализуются на Rust; специализированные OCR/PDF-инструменты не требуется переписывать на Rust.

Redis, Elasticsearch, ClickHouse и графовая база в блок 1 не добавляются без измеренной необходимости. Конкретное S3-хранилище, UI-стек, модели, embedding-модель и поисковый провайдер выбираются перед соответствующим этапом. OpenRouter и Perplexity — возможные адаптеры из описания, а не утверждённые обязательные поставщики.

Система разработки ASTRA → Claude Code не является системой продуктовых агентов OTDEL. Claude Code пишет приложение; продуктолог, исследователь и проверяющий исполняются приложением через его собственные адаптеры моделей.

## 4. Роли и полномочия

| Роль | Задание | Не может |
|---|---|---|
| Продуктолог | Выделить предложения, собрать знания, сформировать пробелы и исследовательские задания | Самостоятельно разрешить публикацию в обход правил |
| Исследователь | Ответить на ограниченные отраслевые вопросы с источниками | Приписать партнёру свойства конкурента, бесконечно расходовать бюджет |
| Проверяющий | Сопоставить утверждения с оригиналами, обнаружить ошибки и противоречия | Выдать согласие модели за независимую сертификацию |
| Rust-обработчики | Хранение, парсинг, очередь, доступ, валидация схем, публикация | Подменить неизвестные сведения догадками |

Это роли общего механизма, не отдельные постоянно работающие нейросети. Контекст каждого запуска ограничен бюро, партнёром, продуктами и входной версией. Внешние документы и страницы — недоверенные данные. Агентам не выдаются произвольный SQL, shell, ключи или инструменты изменения прав.

## 5. Пользовательский путь и каналы приёма

Владелец нажимает «Добавить партнёра», задаёт название или рабочее обозначение, прикладывает материалы и, при наличии, ИНН, сайт, контакт и пояснение. Извлечённые реквизиты считаются кандидатами до проверки; ИНН не выдумывается по названию. Один партнёр может иметь несколько направлений.

Первая последовательная реализация — веб-загрузка PDF и изображений с проверкой на BASIS. Далее внутри блока добавляются DOCX, XLSX, PPTX и веб-ссылки. Старые бинарные офисные форматы требуют отдельного конвертера: до его проверки интерфейс явно сообщает о неподдерживаемом формате.

Целевые дополнительные входы: ограниченная ссылка загрузки для партнёра, API, почтовый вход, Telegram/бот и папка внешнего диска. Каждый подключается отдельно с проверкой доступа и повторной доставки; перечень на схеме не означает готовность всех интеграций. Видео/YouTube требуют отдельного разрешённого способа получения и транскрипции. Неподключённые входы не показываются как рабочие.

Публичная ссылка партнёра ограничивается партнёром, сроком, размером и количеством загрузок; она не даёт доступ к просмотру чужих документов. Расширенные каналы не блокируют проверку основного пути через веб.

## 6. Семь этапов обработки

### 6.1. Приём и сохранение

Потоковая загрузка, проверка фактического типа, размера, читаемости, опасного содержимого; карантин до завершения проверок. Вложения не исполняются. Сохраняются оригинал, хеш, источник, дата получения и версия.

Дедупликация учитывает область партнёра. Совпадение хеша с чужим закрытым файлом не раскрывается. Изменённый каталог — новая версия. Повторная обработка тем же parser/model/prompt-профилем использует сохранённый результат; явный запуск новой версии обработчика допускается.

### 6.2. Извлечение структуры

Текстовый слой читается напрямую; страницы без полезного текста направляются в OCR/анализ изображений. Сохраняются заголовки, разделы, таблицы, единицы, сноски и привязки к страницам/областям. Для таблиц XLSX — лист и ячейки.

Для каждой страницы известен исход: извлечена, пустая, требует распознавания, ошибка или неполная обработка. Ошибка одной страницы не исчезает за общим статусом «готово». Оригинал доступен для визуальной сверки.

### 6.3. Первичное понимание

Продуктолог получает содержание порциями, выделяет направления, семейства изделий и услуги, связывает документы и продукты, составляет предварительный паспорт и карту пробелов. Общая презентация может относиться к нескольким направлениям.

### 6.4. Фрагменты и точные факты

Текст разделяется по смыслу. Фрагмент хранит цепочку партнёр → продукт → документ → версия → раздел → область источника. Добавленный моделью поясняющий контекст хранится отдельно от оригинальной цитаты.

Точное значение хранится отдельно: предмет, свойство, значение, единица, условия, источник и статус. Табличные значения сохраняются со строкой, столбцом, заголовками, примечаниями и схемой применимости. Неясная ячейка не превращается в ноль.

### 6.5. Ограниченное отраслевое исследование

Вход — конкретные вопросы продуктолога. Исследователь получает лимиты запросов, страниц, проходов, времени и стоимости. Останавливается при достаточном покрытии, исчерпании бюджета, повторяющихся сбоях или отсутствии новых оснований.

Поисковый результат — средство обнаружения источника. Для существенного факта требуется доступное подтверждающее содержимое; сниппет или ответ поисковой модели сам по себе не заменяет документ. Сохраняются URL, даты, доступная версия и область цитаты.

Отраслевой контекст отделяется от возможностей партнёра. Общедоступные знания могут переиспользоваться при явной классификации; закрытые документы никогда не становятся общей библиотекой автоматически.

### 6.6. Сборка знаний

Результат: паспорта партнёра и направлений, характеристики и ограничения, глоссарий, карта применений, необходимые параметры подбора, Q&A, аргументы с основаниями и пробелы. Синонимы не объединяют разные изделия без доказательства. Тексты для общения — производные представления, связанные с фактами.

Экспорт описания/презентации — результат работы базы, не её замена. Экспорт должен учитывать ограничения раскрытия и не добавлять отсутствующие коммерческие условия.

### 6.7. Проверка и автоматическая публикация

Проверяющий сопоставляет утверждения с оригиналами. Rust проверяет схемы, ссылки, область доступа, обязательные условия, состояние источников и правила готовности. Совпадение ответов двух моделей не является доказательством.

Статусы утверждения: `source_supported`, `hypothesis`, `unknown`, `conflicted`, `stale`. `source_supported` означает поддержку источником, а не независимую гарантию истинности. Сохраняются автор утверждения, область, дата и ограничения.

Версия публикуется автоматически при прохождении правил. Пробелы могут ограничивать отдельные применения, не блокируя все знания. Недостоверная таблица запрещает численный ответ по этой таблице, но не обязательно описание семейства продукта.

## 7. Готовность и жизненный цикл

Обработка: `queued → running → completed / partial / failed / waiting_input / budget_exhausted / cancelled`. Текущий этап хранится отдельно; правила повторов различают временные и постоянные ошибки.

Версия знаний: `draft → validating → published / blocked`; опубликованная версия может стать `superseded` или `revoked`. Публикация атомарно переключает указатель на неизменяемый снимок фактов, фрагментов и результатов проверок.

Отдельно определяется готовность к описанию продукта, формированию гипотез аудитории, ответам о характеристиках и ответам о коммерческих условиях. Это доступность знаний, а не разрешение отправлять сообщения, обещать совместимость или принимать обязательства.

Старый завершившийся запуск не может перезаписать более новую входную ревизию. Если новый источник опровергает старый факт, старый факт оперативно исключается из разрешённого использования; ожидание новой публикации не позволяет продолжать известную ошибку. Откат не воскрешает отозванные источники.

## 8. Модель данных

Логические сущности, окончательные миграции проектируются перед реализацией:

- Бюро, пользователь, членство и права; партнёр и представитель.
- Продуктовое направление, семейство, изделие и связи с документами.
- Источник, версия источника, объект файла, страница/структурный элемент и область доказательства.
- Утверждение с типизированным значением, единицей, условиями, датами и связями с доказательствами.
- Чанк, embedding-профиль, вектор, контекст и привязка к версии.
- Термин, значение термина, синоним, применение, Q&A и их зависимости от фактов.
- Пробел, исследовательское задание, уточнение партнёру и статус доставки.
- Запуск обработки, задача, попытка, резерв/фактический расход и событие журнала.
- Версия знаний, результаты проверки и матрица готовности.

Обязательные свойства: scope бюро/партнёра; неизменяемые источники; доказательства не теряются при обновлении; источник и время различаются; ИНН хранится строкой; числа/единицы не превращаются в свободный пересказ; embedding-модель и размерность версионируются.

RLS применяется к рабочим ролям без superuser/BYPASSRLS и владения таблицами; миграции идут отдельной ролью. Контекст доступа задаётся сервером внутри транзакции, не берётся на доверии из запроса модели. Проверяются API, фоновые задачи, файлы и кэш; одного RLS недостаточно для изоляции S3.

## 9. Поиск для других агентов

Запрос включает задачу, продукт и закреплённую версию. Сервер проверяет доступ. Точные артикулы и параметры ищутся структурно, термины — текстовым поиском, смысл — векторами; результаты объединяются и проверяются на применимость.

Возврат: ответимые факты, условия, цитаты, источники, версия и неизвестное. В один ответ не смешиваются разные версии. При отсутствии ответа возвращается пробел. Неразрешённые данные не передаются модели с надеждой, что она их проигнорирует.

На небольшом корпусе допустим точный векторный поиск. Переход на ANN подтверждается сравнением полноты с эталоном, в том числе с фильтрами партнёра. Профили embeddings разных моделей не смешиваются в одном пространстве.

## 10. Обновления, очередь и расходы

Триггеры: новый материал, вопрос без ответа, ответ партнёра, срок перепроверки. Это продуктовые механизмы приложения, не созданные сейчас фоновые автоматизации Codex.

Пересчитываются изменённые факты и зависимые представления. Исходная переписка покупателя и прошлый ответ агента не становятся доказательствами характеристик.

Очередь PostgreSQL: короткое взятие задачи, lease/heartbeat, ограниченные повторы, состояние вне памяти worker. Внешние API вызываются вне транзакции; события изменения состояния публикуются через outbox. Ключи идемпотентности не обещают абсолютную однократность у внешнего поставщика.

Перед платным вызовом резервируется бюджет. После — фиксируется расход либо неопределённый исход, требующий сверки. Конкурентные задачи не обходят общий лимит. Нет настроенного бюджета/провайдера — платный этап ожидает настройки, не запускает произвольный сервис.

Изменение поведения агента отделено от пополнения знаний: версии инструкций и поиска проходят регрессионный набор перед продвижением. В первом релизе агент не меняет собственные правила публикации или полномочия.

## 11. Интерфейс

Карточка партнёра содержит: обзор, продукты, материалы, знания, пробелы, версии и историю обработки. Это разделы одного процесса, не обязательные отдельные приложения.

После загрузки видны этап, уже выполненная работа и причина ожидания. Не показывать выдуманный процент или фиксированное время ИИ-обработки. Характеристика открывает исходную страницу с нужной областью. Пробел показывает, какие ответы он блокирует.

Пользователь может повторить исправимый сбой, добавить материалы, ответить на вопрос, исправить вывод с основанием, просмотреть изменения или отозвать версию. Нормальный путь не требует ручной работы между этапами.

## 12. Последовательность реализации внутри блока

| Этап | Результат для проверки |
|---|---|
| 1A. Приём | Партнёр, веб-загрузка, оригиналы, изоляция, очередь и статусы; оба BASIS PDF сохранены |
| 1B. Чтение | 32 + 12 страниц учтены, текст и изображения обработаны, таблицы и ошибки видны |
| 1C. Понимание | Продуктолог создаёт направления, факты, глоссарий, применения и пробелы |
| 1D. Исследование | Ограниченные задания с бюджетом и доказательствами, разделение отрасли/партнёра |
| 1E. Публикация и поиск | Проверяющий, автоматические правила, версии, готовность, ответы с источниками |
| 1F. Обновления и завершение | Новые версии/вопросы, регрессии, оговорённые форматы, проверка восстановления и полный прогон |

В каждом этапе Claude реализует ограниченное задание, Codex независимо проверяет diff и соответствующие тесты, исправления возвращаются в ту же сессию. Следующий этап начинается после проверок предыдущего. Блок 2 — только после приёмки всего согласованного объёма блока 1.

## 13. Проверки приёмки

1. BASIS: все 44 страницы учтены; презентация не объявляется пустой; нечитаемый фрагмент обозначен.
2. Контрольная выборка численных таблиц сверена с изображениями: профиль, длина, толщина, нагрузка, единицы и схема опирания. Эталон фиксирует проверяющий, а не извлекающий агент.
3. Извлечённый факт открывает правильную версию документа и страницу/область; добавленный контекст не выдаётся за цитату.
4. Повторная загрузка/доставка задачи не создаёт второй опубликованный результат; обновлённый файл создаёт новую версию.
5. Нет цены/срока/данных для подбора — ответ сообщает об отсутствии и создаёт пробел; не подставляет рыночную догадку.
6. Противоречащие источники, устаревшие условия, неизвестный термин и чужое изделие не дают уверенный численный ответ.
7. При выполненных правилах версия публикуется без обязательного клика человека; частичная готовность не выглядит как полный коммерческий допуск.
8. Партнёр A не получает данные B через поиск, API, файл, кэш или worker; проверяется рабочая роль базы.
9. Инструкция внутри PDF/сайта не меняет права и назначения инструментов. Загрузчик ограничивает схемы URL, внутренние адреса, редиректы, размер и время; документы обрабатываются с ресурсными лимитами.
10. Прерванный worker восстанавливает обработку; запоздавший результат не перезаписывает новую ревизию; восстановление файлов и БД сохраняет ссылки.
11. Исчерпание бюджета, отказ модели и неизвестный исход запроса видны; скрытого бесконечного исследования нет.
12. Вопросы проверяются на отдельном наборе: точный артикул, перефразирование, отрицательный ответ, противоречие, ограничение применения и чужой партнёр. Ошибки поиска и генерации измеряются отдельно.

Производительность измеряется отдельно для загрузки, обработки, поиска без генерации и ответа модели. Отчёт содержит размер корпуса, оборудование, конкурентность, p50/p95, ошибки, память и расходы. Пороговые значения фиксируются до нагрузочной приёмки; пока показатели не измерены.

## 14. Решения перед конкретными интеграциями

Нужно определить размещение и объём ресурсов, хранилище, доступ к моделям/OCR/поиску, допустимые данные для передачи и бюджет исследований. Это не мешает начать 1A, но нельзя объявить готовым весь автоматический блок с одними заглушками. Конкретные версии зависимостей фиксируются при реализации.
