# claude-worker-v1 — проверенная локальная конфигурация Claude Code MCP

## Конфигурация подключения (точно проверено)
- Команда: `npx`
- Аргументы: `[-y, @leo000001/claude-code-mcp]`
- Переменные окружения: пусто (нет заданных env)
- Наблюдаемая версия: `2.8.11`
- Реализация воркера: на базе Agent SDK (Claude Agent SDK)

Никаких иных настроек сервера, кроме перечисленных выше, в этой конфигурации нет — не выдумывать несуществующие параметры.

## Асинхронный цикл работы (loop)
1. Codex запускает задачу через `claude_code` (async start) с обязательными для **старта** параметрами:
   - явный абсолютный `cwd`;
   - `advanced.persistSession = true`;
   - `permissionRequestTimeoutMs = 300000`.
2. Codex опрашивает статус через `claude_code_check`, передавая ранее полученный `nextCursor` как параметр `cursor` (курсорная пагинация событий), пока задача не перейдёт в терминальное состояние (`idle`/`error`/`cancelled`) или не потребует разрешения.
   - **Важно:** состояние `idle` означает, что воркер закончил текущий запуск (перестал работать), а не что результат принят Codex. После `idle` Codex обязан изучить финальный результат, текст ошибки (если есть) и реально изменённые файлы/проверки, прежде чем считать задачу выполненной.
3. Если воркеру нужно разрешение на действие (permission request) — Codex получает его в статусе и отвечает через `claude_code_check` (`respond_permission`) в пределах дедлайна `permissionRequestTimeoutMs`.
4. Для правок/уточнений в рамках уже идущей задачи Codex использует `claude_code_reply`, передавая `sessionId` и новый `prompt` (персистентная сессия наследует `cwd` и `advanced` из старта — повторно их указывать не нужно и не следует). Реплай отправляется **только** после того, как текущий запуск воркера завершился (`idle`, либо восстанавливаемый `error`) или был явно прерван через `claude_code_session` — не отправлять реплай поверх ещё активного запуска.
5. Для инспекции состояния или прерывания активной сессии используется `claude_code_session`.
6. Codex сохраняет `sessionId` (для всех последующих вызовов по этой сессии) и `nextCursor` (передаётся как `cursor` только в `claude_code_check`). `resumeToken`, если он возвращён, сохраняется отдельно и используется только при восстановлении сессии через `diskResumeConfig`, когда это поддерживается — это не универсальное поле для каждого вызова.

## Опрос без busy-loop
- Не опрашивать сервер чаще, чем это разумно — учитывать рекомендованный интервал опроса сервера (server interval), если он указан в ответе.
- Соблюдать дедлайн разрешения (`permissionRequestTimeoutMs`): не давать ответу на permission-запрос "протухнуть".
- Каждый отдельный вызов ожидания/опроса — не дольше **60 секунд**, чтобы оркестратор (Codex) сохранял возможность вмешаться, отменить или переключиться на другую задачу между вызовами.

## Профиль разрешений по умолчанию (концептуальный)
Базовый (default) набор инструментов для типовой задачи редактирования:
- `Read`, `Glob`, `Grep` — чтение и поиск;
- `Write`, `Edit` — изменение файлов;
- `Bash` — по возможности ограничивать **конкретным набором реально нужных команд** для задачи (например, запуск линтера/тестов), а не общим доступом к shell.

Важные уточнения о том, как это на самом деле работает:
- `allowedTools` (например, список `Read, Write, Edit`) заранее одобряет **тип инструмента** — это не файловая песочница и само по себе **не ограничивает** воркера путями внутри `cwd` или списком owned files.
- `strictAllowedTools` ограничивает **набор доступных инструментов** (например, запрещает `Bash`, оставляя только `Read/Write/Edit`), но тоже не является ограничением по файловой системе.
- Owned files, проверка permission-запросов и ревью помогают контролировать область работы, но не обеспечивают техническую изоляцию файловой системы. Для технической изоляции нужен отдельно настроенный и проверенный механизм.
- `advanced.sandbox` может задавать рантайм-песочницу для выполнения, **если это поддерживается** конкретной версией сервера/моделью — это конфигурируемая опция, а не гарантированно включённая по умолчанию функция. Использовать её как явный параметр запроса, когда нужна повышенная изоляция, и не полагаться на неё, если поддержка не подтверждена.

Это концептуальный профиль по умолчанию, а не жёсткая настройка сервера — конкретные `allowedTools`/`strictAllowedTools` формулируются под каждую задачу отдельно.

## Шаблон task prompt (для запуска через `claude_code`)
```
Цель: <что нужно сделать, одним-двумя предложениями>
Owned files (область владения, поведенческое ограничение — не техническая песочница): <точный список файлов/директорий, которые можно менять>
Контекст: <ссылки на требования/архитектуру/предыдущие решения Codex>
Ограничения: <что нельзя делать: не трогать другие файлы, не коммитить, не мержить и т.п.>
Критерии приёмки: <проверяемый список условий "готово">
Ожидаемый отчёт: <что должно быть в финальном ответе воркера — изменённые файлы, вывод тестов, риски>
```

## Примеры вызовов протокола (JSON)

### Старт задачи (`claude_code`)
```json
{
  "tool": "claude_code",
  "arguments": {
    "prompt": "Цель: ...\nOwned files: ...\nКонтекст: ...\nОграничения: ...\nКритерии приёмки: ...\nОжидаемый отчёт: ...",
    "cwd": "/absolute/path/to/project",
    "model": "sonnet",
    "effort": "high",
    "allowedTools": ["Read", "Glob", "Grep", "Write", "Edit"],
    "permissionRequestTimeoutMs": 300000,
    "advanced": {
      "persistSession": true
    }
  }
}
```

### Продолжение сессии (`claude_code_reply`)
```json
{
  "tool": "claude_code_reply",
  "arguments": {
    "sessionId": "<sessionId, полученный из ответа на старт>",
    "prompt": "Найдена ошибка в X: <описание>. Исправь, сохранив остальную область без изменений.",
    "permissionRequestTimeoutMs": 300000
  }
}
```
Поля `cwd` и `advanced` в `claude_code_reply` не указываются — они наследуются из исходной сессии.

### Опрос статуса (`claude_code_check`)
В первом опросе `cursor` равен 0; далее подставлять числовой `nextCursor` из предыдущего ответа.
```json
{
  "tool": "claude_code_check",
  "arguments": {
    "sessionId": "<sessionId>",
    "action": "poll",
    "cursor": 0,
    "responseMode": "delta_compact"
  }
}
```

## Жизненный цикл worktree (когда появится git-репозиторий)
1. Убедиться, что есть верифицированный базовый коммит (verified common base) в основной ветке.
2. Для каждой независимой параллельной задачи создать отдельный `git worktree` + отдельную ветку от этой базы.
3. Воркер работает только внутри своего worktree, не трогая другие worktree/ветки.
4. По завершении задачи — Codex проводит независимое ревью диффа в этом worktree.
5. После успешного ревью и тестов Codex интегрирует изменения (merge/rebase) в контролируемом порядке, сохраняя изменения пользователя.
6. Автоматический push или merge в защищённую ветку без явного решения Codex/пользователя — запрещён.
7. Worktree удаляется/архивируется **только после** того, как все нужные изменения из него сохранены (влиты/перенесены) в основную линию и в worktree не осталось уникальных незакоммиченных изменений. Удалять worktree "по завершении" без этой проверки нельзя — так можно потерять работу.

На дату настройки (2026-09-13) в текущем проекте нет git-репозитория — этот раздел применяется, когда в рамках конкретной проектной задачи будет создан репозиторий и verified base commit (это не запрещено на будущее, просто не требуется для текущей настроечной задачи).

## Чек-лист завершения задачи
- [ ] Опрос доведён до терминального статуса (`idle`/`error`/`cancelled`); учтено, что `idle` = "воркер закончил запуск", а не "результат принят".
- [ ] Задача выполнена в пределах заявленных owned files (поведенческое ограничение), без выхода за рамки.
- [ ] Получен отчёт воркера: изменённые файлы, фактический вывод тестов/проверок, риски.
- [ ] Codex провёл независимое ревью диффа.
- [ ] Пройдены соответствующие задаче тесты/проверки.
- [ ] Ошибки (если были) отправлены на исправление в ту же сессию (`claude_code_reply`, после завершения/прерывания текущего запуска), без бесконечных повторов.
- [ ] Статус задачи зафиксирован в `docs/worker-runs/<task>.md` (без секретов), если задача — часть реального проекта.
- [ ] Нет несанкционированных коммитов/push/merge в защищённые ветки.
- [ ] Перед удалением worktree подтверждено, что все нужные изменения сохранены и уникальных незакоммиченных изменений не осталось.

## Прочее
- Все правила в этом документе — локальные для данного проекта; они не подразумевают изменение глобальной конфигурации MCP или системных настроек за пределами текущего репозитория.

Сессия после `cancel`/`cancelled` не возобновляется. Для остановки с возможностью продолжения использовать `interrupt`; после ошибки сначала проверить, допускает ли сессия продолжение.
